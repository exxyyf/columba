# Этап 8. Визуализация нарушений и веб-интерфейс

**Цель:** бонусы для защиты в порядке «баллы/трудозатраты»:
1) визуализация нарушений (почти бесплатно из уже посчитанных
кейпоинтов), 2) веб-интерфейс. Бонусы 3–5 (сопутствующие патологии,
оценка маскирования, DICOM SR) реализованы позже, на этапе 9.

## Визуализация (`columba/visualize.py`)

`render_violation_overlay` — один кадр → изображение с оверлеем + данные
чекеров. Рисуется:

- позвоночник — центры тел позвонков, ось (midline), рамки найденного
  металла;
- бедро — головка/большой/малый вертел, ось диафиза, линия дефицита поля,
  если высота кадра меньше откалиброванного порога `hip_roi`.

Ключевое свойство: модуль **не содержит ни одного нового геометрического
вычисления** — все примитивы уже существуют как побочный продукт чекеров
(`get_spine_keypoints`, `column_midline`, `metal_components`,
`detect_hip_landmarks`); визуализация — только отрисовка поверх уже
посчитанных точек плюс маршрутизация по региону. Один и тот же PNG отдают
CLI (`uv run python -m columba.visualize`) и сервис (`POST /visualize`).

Побочная проверка: смоук на реальных файлах «Для теста» отрисовал
корректные картинки с первого раза — ориентиры легли на анатомически
ожидаемые места, отдельной калибровки координат для рисования не
потребовалось (те же координаты уже проверены тестами чекеров).

## Веб-интерфейс: свой, а не Gradio/Streamlit

Осознанное отступление от исходной формулировки «веб-интерфейс
Gradio/Streamlit»: сделан собственный статичный HTML/CSS/JS
(`columba/static/`), отдаваемый уже существующим FastAPI-сервисом этапа 7
(`GET /` + статика). Обоснование: Gradio/Streamlit проще в разработке, но
добавили бы отдельный процесс/порт и тяжёлые новые зависимости поверх уже
работающего сервиса — пришлось бы либо дублировать инференс-код, либо
городить прокси между двумя серверами. Свой фронтенд — один процесс, один
порт, ноль новых рантайм-зависимостей, серверная логика не дублируется
вообще (страница вызывает те же `/predict`/`/visualize`, что и любой
другой клиент API).

Поток: выбор `.dcm` → `POST /predict?format=json` → таблица результатов →
клик «Визуализация» на строке → `POST /visualize` с тем же файлом → PNG в
панели. Сервер сознательно **не хранит** загруженные файлы между
запросами: браузер держит выбранные `File`-объекты и пересылает файл
повторно (~100 КБ по localhost) — альтернатива с серверным состоянием
(temp-файлы, TTL, гонки параллельных пользователей) не оправдана для
этой задачи.

## Новый эндпоинт `POST /visualize`

Один DICOM-файл → PNG. Предиктор CNN бедра переиспользует существующий
кэш по пути весов — повторные вызовы не перечитывают веса с диска.

## Тесты

`tests/test_visualize.py` — рендер обоих регионов на реальных кадрах,
PNG-сигнатура, явный CNN-предиктор даёт `status=ok` (без него —
`not_evaluated`, честная деградация), нечитаемый файл — `(None, None)`
без исключения. `tests/test_service.py` — главная страница, статика,
`/visualize` возвращает `image/png`, 400 на нечитаемом файле.

Дальнейшее развитие интерфейса (загрузка папки/ZIP, CSV-экспорт, сводка,
доступность WCAG AA, JSON-ответ визуализации) — этап 9.
