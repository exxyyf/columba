# Этап 7. Сервис и упаковка

**Цель:** FastAPI-сервис, пакетная обработка, фиксация seed,
контейнеризация, инструкция воспроизведения; проверка требований —
лимит 3 мин/исследование, отсутствие внешних вызовов.

## FastAPI-сервис (`columba/service.py`)

Тонкая HTTP-обёртка над `inference.run_inference` — отдельной логики
инференса в сервисе нет:

- `GET /health` — статус, устройство инференса, наличие весов;
- `POST /predict` — плоский батч файлов; ответ CSV в формате сабмита,
  `?format=json` — те же строки в JSON;
- `POST /predict/zip` — архив со структурой исследований (сохраняет
  парное определение стороны бедра).

Безопасность обработки входа: загруженные файлы читаются во временный
каталог с автоочисткой; при плоской загрузке имя приводится к basename
(защита от directory traversal), ZIP фильтруется от абсолютных путей и
`..` (zip-slip). Ошибки входа — 400/422 с человекочитаемой причиной, без
трейсбека наружу. Проверено через `fastapi.testclient.TestClient` (тот же
ASGI-стек, что реальный uvicorn), в том числе на реальных DICOM из
«Для теста»; 8 новых тестов.

## Находка: `default_device()` не видел CUDA

Функция выбора устройства, используемая всеми CNN-предикторами проекта,
проверяла только MPS: на типичном Linux/Docker-хосте с NVIDIA GPU
инференс всегда шёл бы на CPU даже при `--gpus all` — тихая деградация
производительности, незаметная по функциональным тестам (результат тот
же, просто медленнее). Исправлено на порядок CUDA → MPS → CPU; три теста
фиксируют порядок через monkeypatch.

## Docker

Многостадийный `Dockerfile`: `python:3.12-slim`, `uv` копируется из
официального образа, слой зависимостей отделён от кода (кэш сборки).
Один образ для CPU и GPU — PyPI-колесо torch само определяет CUDA в
рантайме; для GPU на хосте нужны драйверы и `nvidia-container-toolkit`.
Веса в образ **не запекаются** — монтируются томом `artifacts/models/`
при запуске, той же конвенцией, что реестр весов установил для локального
рантайма.

На момент этапа образ был написан и вычитан, но не собран (в среде
разработки не было доступа к Docker-демону) — это честно зафиксировано
как открытый пункт, закрытый позже: CPU-вариант сборки и проверка весов
при старте контейнера добавлены на этапе 9, образ собран и проверен на
машине с Docker (сценарии и устранение неполадок — `docs/deployment.md`).

## Проверка требований

| требование | статус |
|---|---|
| Лимит 3 мин/исследование | выполнен с запасом на порядки: ~0,08 с/файл на CPU по полному корпусу из 499 файлов; исследование — обычно 2–5 файлов |
| Отсутствие внешних вызовов | проверено поиском по исходникам (позже усилено AST-тестом на этапе 9: единственный сетевой модуль — `columba.weights`, инференс и сервис его не импортируют) |
| Фиксация seed | `config.SEED = 42` во всех местах со случайностью — было заложено с этапа 0 |
| Модели в отдельном хранилище | конвенция реестра весов с контрольными суммами — с этапа 2; Docker её использует (монтирование, не запекание) |

## Что осталось после этапа (закрыто позже)

1. Сборка и прогон Docker-образа — выполнены на машине с доступом к
   демону; контейнер при старте проверяет размеры и SHA-256 весов и
   отказывается стартовать с повреждёнными файлами.
2. Ссылки на скачивание весов — вписаны в `weights_registry.json` на
   этапе 9 после загрузки в хранилище.
3. Для реального батча закрытого теста рекомендован `/predict/zip` с
   сохранённой структурой папок: плоский `/predict` определяет сторону
   бедра менее надёжным методом `content_only` (отражено в README).
